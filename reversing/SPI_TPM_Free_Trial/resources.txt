IMPORTANT CORRECTIONS TO v2:
  - The firmware has NO budget accounting. Helper 0x1b20 is the response
    header initializer, not a budget updater. All budget checks are in
    userland spi-tpm-service.
  - State offsets 0x2420..0x2434 are SPI frame state-machine fields
    (cursor/limit/lengths/outcap), not firmware budget fields.
  - Decrypt budget formula is COST * (ceil(len/4) + 0x100), not 33*COST.
    For a 4-byte plaintext that is 257*COST. Encrypt is COST*(ceil(len/4)+
    0x20), i.e. 33*COST for 4 bytes. The old "33*COST" statement was
    encrypt-only.
  - Blob bytes +0x18..+0x27 are the 16-byte MAC tag (f1ea0 output), not a
    zero/reserved header area. The ciphertext starts at +0x28. f1ea0
    absorbs blob[0:0x18] (magic/op/hdrlen/nonce/cost/length/field14), then
    the ciphertext at +0x28; the tag is the output and is compared by
    decrypt. This corrects the v3 "reserved16" wording.
  - Blob field14 (+0x14) is produced by 0x3850(slot+0x10), a key-derived
    "bilin" fingerprint, and is then included in the MAC prefix. It is not
    itself the final MAC tag.

V4 CORRECTIONS / NEW FINDINGS (2026-10-25):
  - Outer header +0x0c is NOT a u16 host outcap. The kernel writes a u32
    SPI transfer length (always 0x2004) there; the real COST is at +0x08.
    Firmware 0x3140 reads +0x0c as the transfer limit/outcap, checks
    payload_len+0x18 <= value <= 0x2004, and stores it at state+0x2434.
    Helper 0x1b20 then uses state+0x2434 as the SPI transfer limit.
  - Request length is payload_len + 0x10, not +0x18. The +0x18 is only the
    lower bound for the transfer limit. Firmware request buffer is 0x1010
    bytes (16-byte header + up to 0x1000 payload); response buffer is 0x1008
    bytes at +0x1010..+0x2017; response blob starts at +0x1018.
  - Firmware allows payload <= 0x1000; kernel encrypt caps inlen at 0xfd8
    so blob_len = 0x28 + round4(inlen) <= 0x1000 fits the response buffer.
    Kernel decrypt caps inner length at 0xfd8 and requires outcap >= it.
    Service caps both plaintext and inner length at 0x400. No firmware or
    kernel buffer overflow into key slots was found.
  - Decrypt processing 0x2c5c validates embedded op=2, hdrlen=0x28,
    cost in [1,0xf4240], length <= 0xfd8, and

    f1ea0, requires a unique 16-byte tag match, then checks field14 via
    0x3850 and writes plaintext to state+0x1018.
  - COST is fully authenticated, not truncated. f1ea0 absorbs blob[0:0x18]
    (including the full 32-bit cost) and f33d0 multiplies the full 32-bit
    cost by 0xa5a3564e27f8862f. Patching cost to 1 (remote live) or 3
    (local live, same low 4 bits) fails; the cost-3 blob passes the service

4. FIRMWARE (libspi_tpm_firmware.so)
================================================================================

x86-64 ELF shared object, stripped. .text VA 0x1100-0x3ac5; file offset == VA
through .text/.rodata. .rodata VA 0x4000-0x41c8. Only exported symbol:
spi_tpm_fw_get_api_v1 @ 0x3200.

--- 4.1 API table (VA 0x5d20) ---

  +0x00  version=1, table size=0x58
  +0x08  "spi-tpm-firmware" string pointer (0x4012)
  +0x10  "1" string pointer (0x4023)
  +0x18  0x1d50  create(out_state, size_check_ptr)
  +0x20  0x1a40  destroy(state)
  +0x28  0x2350  reset_to_defaults(state)
  +0x30  0x3040  feed(state, byte) -> response byte / status
  +0x38  0x1a00  get_required_state_size() -> 0x24b8
  +0x40  0x1a70  save_snapshot(state, out, out_len, *required)
  +0x48  0x23c0  restore_snapshot(state, snapshot, snapshot_len)
  +0x50  0x1a10  get_error_string(state)

  Note: +0x38/0x1a00 returns 0x24b8 and is the migration snapshot size,
  not the SPI request length. The SPI request/response buffers live inside
  the 0x24b0 state (see 4.2).

create: calloc(1,0x24b0), calls 0x1ca0 (reseed) then 0x1ad0 (init defaults).
Fails closed (wipes + frees + returns -1) if reseed fails.

reset: memset(state,0,0x24b0), calls 0x1ca0, then ALWAYS tail-calls 0x1ad0.
If reseed failed it writes "failed to reseed firmware key table" into
state+0x2444 first, but still proceeds.

save_snapshot: 8-byte header "WFRC" + u32 version=5 + 0x24b0-byte state.
Total 0x24b8 bytes.

restore_snapshot: validates WFRC magic, version==5, length==0x24b8 exactly.
Mallocs a new 0x24b0 state, memcpy's payload, then only checks consistency of
SPI frame-state fields 0x2420/0x2424/0x2428/0x242c/0x2430/0x2434. There is NO
hash/MAC/signature check. If reachable, a forged snapshot is accepted
wholesale. Reachability is still unproven; see 4.11.

--- 4.2 State layout (verified with a local ctypes harness) ---

  0x0000..0x100f  request frame buffer. 16-byte header + payload; 0x1010
                  bytes total. Firmware allows payload <= 0x1000; kernel
                  encrypt caps inlen at 0xfd8 so the response blob fits.
  0x1010..0x2017  response buffer (0x1008 bytes).
                  0x1010: a5, opcode, u16 response length, u32 status
                  0x1018: response blob ("STP1"...) or decrypt plaintext
                  Max response payload: 0x1000 (encrypt blob, inlen=0xfd8)
                  or 0xfd8 (decrypt plaintext). Both end <= +0x2017.
  0x2020..0x241f  8 key slots, 0x80 bytes each.
                  slot+0x00: key id (u32)
                  slot+0x10: 48 bytes of real key material
                  slot+0x70: valid flag byte
  0x2420          SPI cursor
  0x2424          SPI limit
  0x2428          request total length (payload+16)
  0x242c          response/request bookkeeping
  0x2430          response length
  0x2434          SPI transfer limit/outcap from outer header +0xc (u32;
                  kernel always sends 0x2004). Real outer COST is at +0x08.
  0x243c          session nonce seed (4 bytes, from getrandom)
  0x2440          per-request MAC accumulator (u32, XORed during cipher/MAC)
  0x2444          error string buffer

The reset defaults at .rodata 0x4130 are:
  0x2420 = 0, 0x2424 = 0x10, 0x2428 = 0x10, 0x242c = 0x10, 0x2430 = 0.
These are SPI state-machine values, NOT a firmware budget.

--- 4.3 Entropy / reseed path ---

0x1ca0: calls getrandom-wrapper 0x1b90 for a 4-byte session seed stored at
state+0x243c. If that single getrandom fails, it returns immediately and NO
slots are reseeded. Otherwise it loops all 8 key slots (0x2020..0x2420,
0x80 apart), calling 0x1bf0 per slot.

0x1bf0: getrandom(64 bytes) into a local buffer; on success zeros the 0x80-byte
slot, then calls 0x34a0(slot+0x10, random_buf) to derive the real key material;
wipes the local random buffer; returns getrandom success/fail.

The .so runs on the challenge host (x86-64), so getrandom draws from the host
entropy pool. The "entropy failure -> blank/zero key slot" path is a real code
smell but very unlikely to be remotely triggerable. Low priority.

Reseeding fills key material but does not by itself mark a slot valid; genkey
assigns the key id and sets slot+0x70.

--- 4.4 BLAKE2s core ---

0x1200 = compress, 0x1df0 = streaming update. CONFIRMED byte-exact against
Python hashlib.blake2s on 11 inputs (0,1,63,64,65,127,128,129,200 bytes).

  - .rodata 0x4080-0x411f is the stock, unmodified BLAKE2 SIGMA table
    (10 rows, row 0 identity, row 1 {14,10,4,8,9,15,13,6,1,12,0,2,11,7,5,3}).
    0x1200 loops exactly 10 times over it.
  - The "0x4160 spells ble..." oddity is the tail of the error string
    "failed to reseed firmware key table", not crypto.
  - Rotation constants 16,12,8,7; standard IVs embedded as immediates in
    0x1200 (e.g. mov r9d,0x6a09e667 at 0x1245).
  - compress state layout: h[8] at 0x00-0x1f, t0 at 0x20, t1 at 0x24,
    m[16] at 0x28-0x67.
  - .rodata 0x4140-0x415f is a SECOND 8-word IV table, identical to the
    standard BLAKE2s/SHA-256 IV except word 0 = 0x6b08c677 instead of
    0x6a09e667. It is used ONLY by 0x1ea0 (the MAC), never by compress().

--- 4.5 SPI frame protocol / dispatch ---

0x3040 models the SPI shift register. Each feed() call writes one byte into
state+cursor (cursor at state+0x2420), starting at offset 0.

First 16 bytes are the request header (confirmed from kernel 0x5b8 and
firmware 0x3140):
  +0x00  byte  0xa5 sync
  +0x01  byte  opcode
  +0x02  u16   declared payload length
  +0x04  u32   key id
  +0x08  u32   COST (real user/startup cost)
  +0x0c  u32   SPI transfer length (kernel always 0x2004); the firmware
               calls this the outcap/transfer limit and stores it at
               state+0x2434 if payload_len+0x18 <= value <= 0x2004.

When the 16-byte header is complete, 0x3140 parses it:
  - transfer limit (dword at +0xc) must be >= declared_len+0x18 and
    <= 0x2004; then stored at state+0x2434. If out of range, the previous
    value is retained. Kernel always sends 0x2004, so this always passes.
  - declared_len must be <= 0x1000; otherwise the firmware returns the
    8-byte error response a5 e3 00 00 00 00 00 00 and sets limit = cost
    (or 0x18 if cost is zero).
  - state+0x2428/0x242c/0x2424 are set to declared_len+0x10, allowing that
    many payload bytes to be written contiguously. Request total is
    payload_len + 0x10 (16-byte header + payload), not +0x18.
  - if declared_len == 0, 0x25e0 is invoked immediately; otherwise after the
    full payload has been shifted in.

Response initializer 0x1b20(state, status, length):
  - memset(state+0x1010, 0xff, 0x1008)
  - state+0x1010 = 0xa5; +0x1011 = status; +0x1012 = u16 length;
    +0x1014 = 0
  - state+0x2430 = length + 8
  - if state+0x2434 != 0: state+0x2424 = state+0x2434 (normally 0x2004)
    else: state+0x2424 = state+0x242c + response_len
  - Encrypt calls 0x1b20 with length = blob_len = 0x28+round4(inlen);
    decrypt calls it with length = inner plaintext length. The response
    payload is then written at state+0x1018.

0x25e0 dispatches on opcode:
  1 = genkey (handler around 0x2627)
  2 = encrypt (handler 0x2780)
  3 = two sub-paths:
      - magic 0x31505453 ("STP1" LE) at request+0x10 -> decrypt (0x2c5c)
      - magic absent and payload length <= 0x27 -> short form, role not fully
        pinned down (budget query/report is a working guess)
  anything else = generic syntax error

Response is written to state+0x1010:
  +0x1010  a5, opcode, u16 length, u32 status
  +0x1018  blob
Kernel module parses this response, including error opcodes such as 0xe4
(ENOKEY).

--- 4.6 Encrypt (opcode 2, handler 0x2780) ---

- Reads KEY at header+4. Searches all 8 slots for slot[0]==KEY and
  slot[0x70]!=0.
- Reads COST at header+8; validates (COST-1) <= 0xf423f, i.e. COST in
  [1,1,000,000].
- Validates declared length <= 0xfd8.
- Obtains 4 fresh bytes via getrandom() as the per-request nonce.
- Calls 0x1b20 to initialize the response header (NOT a budget update):
  0x1b20 memsets response, writes a5/opcode/u16 length/status, sets response
  length at 0x2430 = payload+8, and adjusts the SPI limit at 0x2424.

Response blob format (verified against captures):
  +0x00  8B  "STP1" + u16 opcode=2 + u16 hdrlen=0x28
  +0x08  4B  nonce
  +0x0c  2B  COST & 0xffff
  +0x0e  1B  (COST >> 16) & 0xff
  +0x0f  1B  zero
  +0x10  2B  declared plaintext length
  +0x12  2B  zero
  +0x14  4B  field14 = 0x3850(slot+0x10), key-derived "bilin" fingerprint
  +0x18  16B MAC tag (f1ea0 output; compared by decrypt)
  +0x28  ciphertext, ceil(declared_length/4)*4 bytes

Per 4-byte plaintext chunk (last chunk zero-padded):
  a  = f17e0(plaintext_word, nonce, chunk_index, COST, flag=0)  # F0
  b  = f3700(slot+0x10, a, COST, flag=0)                        # G
  cw = f17e0(b, nonce, chunk_index, COST, flag=1)               # F1
  state+0x2440 ^= (COST + b)
  ciphertext_word = cw

This is a full permutation, not plaintext XOR keystream. Decrypt runs the
inverse chain (see 4.7): b = F1_inv(cw); a = G_inv(b); P = F0_inv(a).

After the chunk loop, 0x1ea0 computes the keyed MAC over the blob (see 4.7).
The blob's field14 is the 0x3850 fingerprint, not the final MAC.

--- 4.7 Decrypt / per-slot MAC (opcode 3 magic branch, 0x2c5c) ---

The request is an OUTER frame (opcode 3) embedding the user blob at outer+0x10
(outer+0x10 == blob+0x0). Validations, in order:
  - embedded op == 2
  - embedded hdrlen == 0x28
  - embedded COST in [1,1,000,000]
  - embedded length <= 0xfd8
  - outer declared payload length == round_up(embedded_length,4)+40 exactly
    (the service's normal decrypt wrapper satisfies this; see 6.5)

No KEY is supplied. The firmware loops ALL 8 slots unconditionally. For each:
  hash = f1ea0(state, slot, blob, rounded_length, local_16B_output)
and compares the resulting 16-byte tag against the expected tag (via a
16-byte XOR + shift-reduce-to-one-byte comparison). Exactly ONE matching slot
is required to proceed.

f1ea0 absorption (corrected):
  - 64 bytes derived from the slot's real key material (slot+0x10) via 0x3690
  - 24 bytes = blob[0x00:0x18] (magic/op/hdrlen/nonce/cost/length/field14)
  - rounded_length bytes of ciphertext at blob+0x28
  - 13-byte constant "spi-tpm-route" at .rodata 0x4060
  - a 32-round keyed chain using f17e0/f3700/f17e0 and state+0x2440
  - BLAKE2s finalization with is_final=1 at 0x2112 (mov esi,1; call 0x1200)

The 16 bytes at blob+0x18..+0x27 are the MAC tag (f1ea0 output), not part
of the f1ea0 input. Proper BLAKE2s finalization rules out a simple
length-extension attack.
Patching nonce, cost, field14, or ciphertext is not a free win:
cost/nonce/field14/ciphertext are absorbed and break verification. The 16
bytes at blob+0x18..+0x27 are the MAC tag itself, not spare bytes; patching
them breaks the tag comparison. The full 32-bit cost is load-bearing:
f1ea0 absorbs it in blob[0:0x18] and f33d0 multiplies it by
0xa5a3564e27f8862f. No low-16/low-8/low-4 truncation shortcut exists;
patching the flag blob's cost to 1 was confirmed live to return
"error hardware".

On a unique slot match, decryption runs the inverse-permutation chain:
  b = F1_inv(Cw); a = G_inv(b); P = F0_inv(a)
where F0/F1 are f17e0(..., flag=0/1) and G is f3700(..., flag=0/1). It is
NOT the same forward chain as encryption; the old "identical encrypt/decrypt
chain" note is superseded. The decrypt loop writes plaintext to state+0x1018.

--- 4.8 Cipher internals ---

v4 UPDATE: the cipher model f33d0/f3700/f17e0 is now implemented in Python
and verified bit-exact against local firmware outputs. The "not bit-verified"
caveats below are superseded. The old "identical encrypt/decrypt chain" and
"ciphertext = plaintext XOR keystream" notes are also superseded. The
verified model is the inverse-permutation chain:
  encrypt: a = F0(P); b = G(a); Cw = F1(b)
  decrypt: b = F1_inv(Cw); a = G_inv(b); P = F0_inv(a)
where F0/F1 are f17e0(..., flag=0/1) and G is f3700(..., flag=0/1).

f17e0(value, nonce, chunk_index, COST, flag_r8) — seed stage high confidence,
final stage carefully transcribed (v4: bit-exact model verified; see update
above):
  seed = (chunk_index * 0x9e3779b9) XOR nonce XOR (COST * 0x735a2d97)
         XOR mask(flag_r8)
  mask = 0xffffffff if flag_r8==0 else 0; mask &= 0xbb03e172;
         mask = (mask - 0x2e4ab5cb) mod 2^32
  six words = [triple32(seed + OFFSET[i]) for i in 0..5]
  OFFSETS = [0x9e3779b9, 0x3c6ef372, 0xdaa66d2b, 0x78dde6e4,
             0x1715609d, 0xb54cda56]
  triple32(x) = x^=x>>16; x*=0x21f0aaad; x^=x>>15;
                x*=0x735a2d97; x^=x>>15   (public lowbias32)
  final 6-round custom ARX finalizer at 0x1910-0x1972 uses x86 16-bit
  partial-register rotates (rol ax,cl / rol si,cl), rotate amounts 7..12 and
  3,5,7,9,11,13. (v4: bit-exact model verified; caveat superseded.)
  Separate unexplored branch at 0x1998 gated on a second flag byte
  (flag_r9!=0), never exercised by the normal chunk loop.

f3700(slot+0x10, value, COST, flag) — real key entry point:
  Reads 48 bytes of genuine key-slot material into local buffers. When
  flag==0 (encrypt/decrypt/MAC all use this path): loops EXACTLY COST times,
  each iteration calling f33d0(evolving_accumulator, round_index&3,
  8 key bytes, 8 more key bytes), folding results via
      acc = ((f33d0_result XOR acc) << 16) | (acc >> 16)
  CONFIRMED LIVE: COST is the literal f33d0 round count. For a 1-chunk
  encrypt, budget delta is exactly 33*COST.

f33d0(accumulator, round_index_mod_4, key_bytes_a, key_bytes_b) — built from
public 64-bit primitives, combined custom:
  - 0x9e3779b97f4a7c15 (splitmix64 gamma)
  - exact splitmix64 / MurmurHash3-x64 fmix64 finalizer:
    multiplies 0xbf58476d1ce4e5b9 and 0x94d049bb133111eb, shifts 30,27,31
  - additional multiply 0xd6e8feb86659fd93
  - XOR literal 0x62696c696e2d7221 = b"bilin-r!"
  - sibling 0x3850 derives values via 0x32f0 with tags "bilin-a!",
    "bilin-b!", "bilin-c!"; 0x3850 is what produces blob+0x14 field14.
  (v4: bit-exact model verified; caveat superseded.) The remaining gap is
  high-COST key recovery, not transcription. Best empirical path: compare
  real keystreams at COST=1,2,3... under a controlled key (zero plaintext
  reveals keystream directly).

--- 4.10 Budget accounting (userland only) ---

Encrypt handler:

  if required > [sp+0x58]: "error syntax-or-budget"
  else [sp+0x58] -= required

Decrypt handler:
  required = COST * (ceil(length/4) + 0x100)
  if required > [sp+0x58]: "error syntax-or-budget"
  else [sp+0x58] -= required

Live encrypt data (4-byte plaintext):
  COST=1 -> delta 33; COST=5 -> 165; COST=10 -> 330.
  COST=50/100 failed when remaining budget was insufficient.
  COST=1,000,000 failed.
Start budget 1024.

Max decrypt COST for 4 bytes = floor(1024/257) = 3.

--- 4.11 Snapshot save/restore and reachability ---

0x1a70 save and 0x23c0 restore exist in the HOST-SIDE firmware .so. The
AArch64 service and kernel module have no direct xrefs to these host addresses;
they only speak SPI frames through the QEMU device. Reachability would require
the QEMU device/migration/vmstate code to call save/restore, or another host
path. No such caller has been found yet.

If reachable, 0x23c0 accepts a forged WFRC v5 snapshot with only loose SPI
state-field bounds checks and no cryptographic integrity check. That would
allow arbitrary key slots/state, likely trivial flag decryption. This remains
a live structural weakness, not a proven path.

v4 note: the QEMU spi-tpm migration save/load handlers are around
0x2b18c0/0x2b17f0. The firmware API +0x38/0x1a00 returns 0x24b8 and is the
migration snapshot size, not the SPI request length. The remote runner
exposes no monitor/migration interface; no guest xref or guest-reachable
caller has been found. Treat this as closed unless a new host path appears.

--- 5.1 User ioctl struct (0x38 bytes, copied with _inline_copy_from_user) ---

  +0x00  u32 key
  +0x04  u32 cost
  +0x08  u32 length        (also used as outer frame declared length)
  +0x0c  u32 pad
  +0x10  u32 outcap        (must be <= 0x1000)
  +0x14  u32 status/result (kernel writes error here)
  +0x18  u64 input pointer
  +0x20  u64 output pointer
  +0x28  16 bytes that must be zero (memchr_inv check)

--- 5.2 crypt ioctl behavior ---

Common:
  - length-1 <= 0xfff (i.e. length in [1,0x1000])
  - outcap <= 0x1000
  - input/output pointers nonzero
  - zeros at +0x28..+0x37
  - key and cost nonzero for encrypt

Encrypt (ioctl 0xc0384302):
  - key/cost nonzero
  - length <= 0xfd8
  - opcode 2
  - memdup_user(input, length)
  - response length = round_up(length,4)+0x28
  - output capacity must fit

Decrypt (ioctl 0xc0384303):
  - length > 0x27
  - opcode 3
  - embedded length at input+0x10; if > 0xfd8 -> -90
  - outcap >= embedded length, else -28
  - memdup_user(input, length)
  - kernel does not supply a key; the service's decrypt wrapper 0x9f80
    leaves the user struct key/cost fields zero. The kernel decrypt path
    does not reject this; the firmware ignores the outer key/cost for
    decrypt and identifies the slot by the inner blob's 16-byte tag. The
    outer key id 0 is harmless.

On response:
  - response length is read from transaction state +0x2a (u16)
  - the response parser at 0x7a4 checks outcap (transaction +0x28) >=
    response payload length (response header +2) before copy_to_user;
    the earlier "unchecked copy_to_user" note is superseded.
  - if nonzero, copied to user output pointer
  - status at struct+0x14 is copied back
  - errors: -14 EFAULT, -22 EINVAL, -28 ENOSPC, -90 EMSGSIZE, etc.

--- 5.3 Outer frame / run_transaction ---

spi_tpm_run_transaction (0x5b8) builds the 16-byte SPI frame header:
  +0x00  0xa5
  +0x01  opcode (2 or 3)
  +0x02  u16 declared length (from transaction +0x18 / user struct +0x08)
  +0x04  u32 key
  +0x08  u32 cost (real user/startup COST)
  +0x0c  u32 total SPI transfer length (always 0x2004)
Payload follows at +0x10.

The host outcap is NOT in the outer header; it lives in the kernel
transaction struct +0x28 (u16) and is checked by the response parser at
0x7a4 (outcap >= response payload length) before copy_to_user. The kernel
sends 0x2004 as the SPI transfer length because the SPI core transfer
buffer is 0x2004 bytes; the firmware uses it as its response limit.

Response parsing checks 0xa5 sync and opcode bytes such as 0xe4 (ENOKEY).

No budget logic exists in either module.

--- 6.1 Startup sequence (exact) ---

  0x93d0-0x9450: read /flag into sp+0x118, length in x21.
  0x945c:        call genkey wrapper 0x9dc0 (ioctl 0xc0184301);
                 key id written to sp+0x54.
  0x9468-0x9490: call encrypt wrapper 0x9e80 (ioctl 0xc0384302):
                   x0 = fd (sp+0x50)
                   w1 = key id (sp+0x54)
                   x2 = flag plaintext (sp+0x118)
                   w3 = flag length (x21)
                   w4 = 0x85fb3 (548787)
                   x5 = output blob (sp+0x64)
                   x6 = output length pointer (sp+0x110), initialized 0xa8
                 The constant is built by:
                   0x9474: mov w4, #0x5fb3
                   0x948c: movk w4, #0x8, lsl #16
  0x94a0-0x94b0: zero the 128-byte flag plaintext buffer.
  0x94b4-0x94c0: initialize userland budget:
                   [sp+0x58] = 1024
                   [sp+0x60] = 27
  Then: privilege-drop/init calls, command loop.

The cached blob and length live at sp+0x64 / sp+0x110 for the rest of the
process. get_flag prints them without re-encrypting.

--- 6.2 get_flag budget bypass (DEFINITIVE) ---

get_flag is not privileged and does not bypass a firmware check. The bypass is
simply that the only flag encryption happens at startup, before the userland
budget variable exists, via a direct call to the same ioctl wrapper used by
user encrypt:

  0x9490: bl 0x9e80    with w4 = 0x85fb3

The budget checks exist only inside the text-command handlers:
  - encrypt handler 0x9b24-0x9b54
  - decrypt handler 0x9a0c-0x9a20
The wrapper 0x9e80, kernel module, and firmware have no budget check.

Therefore:
  - get_flag's COST is a compile-time constant, unconstrained by budget.
  - The cached blob is a normal opcode-2 blob under key slot 1.
  - No command in the text protocol can re-run the startup path.

--- 6.3 Normal budget gates (exact) ---

Encrypt (0x9b24-0x9b54):
  plaintext is hex-decoded into sp+0x198 with capacity 0x400; decoded
  length must be 1..0x400 (check at 0x9b30).
  x3 = decoded plaintext length
  w4 = COST
  required = COST * ((length+3)>>2 + 0x20)
  if required > [sp+0x58] -> error syntax-or-budget (branch to 0x98f4)
  else [sp+0x58] -= required
  then call 0x9e80 with plaintext at sp+0x198, output at sp+0x598,
  outcap 0x1000.

Decrypt (0x9a0c-0x9a20):
  w0 = embedded length at blob+0x10
  w1 = embedded COST at blob+0xc
  required = COST * ((length+3)>>2 + 0x100)
  if required > [sp+0x58] -> error syntax-or-budget (b.hi at 0x9a20)
  else [sp+0x58] -= required
  then call 0x9f80 with blob at sp+0x598, output at sp+0x198,
  outcap 0x400.

--- 6.4 Decrypt command validations before the gate ---

At 0x995c:
  - hex-decode into sp+0x598 (capacity 0x1000)
  - decoded length must be > 0x27
  - magic at blob+0 must be "STP1" (0x31505453 LE)
  - blob+4 u16 op must be 2
  - blob+6 u16 hdrlen must be 0x28
  - blob+0x10 length in [1,0x400]
  - blob+0xc COST nonzero
  - decoded length == round_up(embedded_length,4)+0x28 (40)
  - then budget gate above
  - then ioctl decrypt wrapper 0x9f80

--- 6.5 Decrypt x2 / outer-frame flow (resolved) ---

The hex decoder 0x91e8 returns with x2 = last decoded byte (scratch), which
looked like a bug. It is not: immediately after the call, the service reloads
the true decoded length:

  0x99a8: ldr x2, [sp, #40]    ; decoded length stored by 0x91e8

So at 0x9a04 (cmp x2, expected_total) and at the 0x9f80 call, x2 is the true
decoded blob length. The normal decrypt wrapper builds a correct outer frame.
The old "naive replay fails because outer-frame length mismatches" theory is
therefore wrong; the normal replay fails at the budget gate.

--- 6.6 Local proof that only the budget gate blocks replay ---

Local setup:
  - run_local.sh with supplied Image, initramfs, QEMU, firmware.
  - local flag file is hitcon{test}\n.

Experiment:
  1. Extract src/initramfs.cpio.gz.
  2. In the extracted /init (spi-tpm-service), patch ONLY the decrypt budget
     branch at file offset 0x9a20:
       before: a8 f6 ff 54   (b.hi 0x98f4)
       after:  1f 20 03 d5   (nop)
  3. Repack the initramfs and append a cpio overlay containing /flag.
  4. Boot QEMU with the patched initramfs.
  5. Run: get_flag, then send the returned blob unmodified to decrypt.

No crypto, key, nonce, or startup COST was modified. This proves:
  - the flag blob's key/MAC are valid for replay;
  - the service-side budget comparison at 0x9a20 is the sole blocker;
  - the firmware outer-frame length and MAC checks pass for the normal
    service decrypt wrapper;
  - the remaining remote problem is purely bypassing the userland budget
    check (or obtaining a high-COST encryption under key slot 1).

Patched-run details:

--- 6.7 Service stack layout (v4) ---

  sp+0x050  fd
  sp+0x054  key id
  sp+0x058  budget (64-bit)
  sp+0x060  queries (u32)
  sp+0x064  cached get_flag blob (capacity 0xa8)

and flag plaintext are above the budget but below the line buffer, and no
command writes to their offsets.

9. WHAT HAS BEEN TRIED / RULED OUT
================================================================================

Ruled out with good confidence:
  - "Just replay get_flag's blob verbatim" on the unpatched service: fails at
    the service budget gate, not at the firmware outer-frame check. With the
    gate NOPed locally, the same blob decrypts correctly.
  - "Keystream never uses the real key": wrong; f3700/f33d0 uses 48 bytes of
    slot key material.
  - "Patch the blob's cost field down": breaks the MAC (cost is absorbed).
    Confirmed statically and live (Test A).
  - Simple length-extension on the per-request MAC: f1ea0 finalizes BLAKE2s
    properly.
  - "Budget-formula collision explains patched-cost failure": no; Test A
    pinned it on cryptographic binding.
  - Obvious integer overflow in the service budget check: cost max 1e6,
    chunks max ~256/1024, product fits 64-bit; no wrap found.
  - Firmware budget bypass: firmware has no budget at all.
  - Service/kernel direct snapshot save/restore xrefs: none found; host-side
    reachability still open.

Useful negative results:
  - Patching nonce, cost, field14, or ciphertext breaks MAC verification for
    every slot.
  - The 16 bytes at blob+0x18..+0x27 are the MAC tag, not spare bytes;
    changing them fails the tag comparison.
  - Decrypt does try all 8 slots, but a unique MAC match is required.

V4 closed routes:
  - Firmware request/response buffer overflow into key slots: closed.
    Payload >0x1000 is rejected by 0x3140; kernel encrypt inlen <=0xfd8
    makes the blob <=0x1000 and the response buffer is 0x1008 bytes;
    service caps at 0x400. Response lengths always match the written data.
  - Cost truncation / low-bit equivalence: closed. The full 32-bit cost is

13. DELIVERABLE (b) WRITE-UP: THE get_flag BUDGET BYPASS
================================================================================

The "free trial" is the startup encryption window. spi-tpm-service performs
the only flag encryption at boot, before the userland budget exists:

  0x945c  genkey wrapper 0x9dc0 -> key slot 1 (key id 1)
  0x9490  encrypt wrapper 0x9e80 with:
            key id    = 1
            plaintext = /flag (sp+0x118)
            COST      = 0x85fb3 (built at 0x9474/0x948c)
            output    = cached blob (sp+0x64)
  0x94a0  wipe the 128-byte plaintext buffer
  0x94b4  [sp+0x58] = 1024  (budget)
  0x94c0  [sp+0x60] = 27    (queries)

The wrappers 0x9e80/0x9f80, the kernel module, and the host firmware have no
budget accounting. The budget checks exist only in the text-command handlers:
encrypt at 0x9b24-0x9b54 and decrypt at 0x9a0c-0x9a20. Because the startup
call goes directly to 0x9e80, the hard-coded COST=0x85fb3 is never checked
against 1024. The flag is encrypted for free.

get_flag (0x9914) is read-only: it prints the cached opcode-2 blob from
sp+0x64 (and its key id) and does not call the firmware, the ioctl wrappers,
or the budget code. That is the get_flag budget bypass: the ciphertext is
obtained without spending any budget or query on encryption.

What remains is decryption, and that is a separate gate. The cached blob's
inner COST is 0x85fb3 and its length is 70, so the normal decrypt handler
computes:

  charge = 0x85fb3 * (ceil(70/4) + 0x100)
         = 548787 * (18 + 256)
         = 150,367,638

against a budget of 1024. The handler rejects before the ioctl. The firmware
would accept the blob (its key/MAC are valid), but the service never sends it.

Local proof: patch ONLY the decrypt budget branch at file offset 0x9a20
(a8 f6 ff 54 -> 1f 20 03 d5, b.hi -> nop), boot the patched initramfs with
the local hitcon{test}\n flag, run get_flag, and send the returned blob
unmodified to decrypt. The result is:

  plaintext 686974636f6e7b746573747d0a = hitcon{test}\n

This proves the bypass mechanism and proves the only blocker is the userland
decrypt budget comparison. It does not recover the remote flag, because no
remote bypass of that comparison has been found.

Why the obvious shortcuts fail:
  - Patching the blob's COST field: the full 32-bit cost is absorbed by
    f1ea0 (blob[0:0x18]) and multiplied inside f33d0
    (cost * 0xa5a3564e27f8862f). Live cost=1 replay returns "error
    hardware". A local cost=3 replay (same low 4 bits as 0x85fb3) passes
    the 1024 budget with a charge of 780 but also returns "error hardware";
    the tag is not a low-bit function.
  - Replaying a self-made low-COST blob: its tag is valid only for its own
    ciphertext/nonce/cost, not for the flag blob.
  - Buffer overflow into the budget: the budget sits below all large service
    buffers; upward overflows miss it. Firmware request/response buffers are
    exactly sized (payload >0x1000 rejected; kernel encrypt inlen <=0xfd8;
    service <=0x400).
  - SRAM/DMA leak: the QEMU DMA backend does not copy data; the kernel driver
    uses kmalloc buffers because 0x2004 > 0x2000; the SRAM dump is all zero
    after the startup encrypt.
  - Cost/length mismatch between service and firmware: both read the same
    inner blob fields; the service's charge and the firmware's MAC/cipher use
    the same cost and length.

The deliverable (b) answer is therefore: get_flag is free because the flag
was encrypted at startup through the ungated wrapper before the budget was
initialized, and get_flag only replays the cached blob. The decrypt budget
gate is a separate obstacle and remains unsolved remotely.
